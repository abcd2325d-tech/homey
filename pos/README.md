# POS & Inventory Management System

A production-shaped Point of Sale and inventory system for a retail store — the demo data is
set up for a beauty supply shop, but nothing in the system is beauty-specific; it's a general
multi-location retail POS. Features: barcode scanning (USB and camera), sales with
discounts/holds/voids/refunds, product variants (e.g. nail polish by color/size),
lot/expiration batch tracking, a customer loyalty program, purchase orders, stock counts,
reports, and printable/thermal receipts.

- **Backend:** Node.js + TypeScript, Express, Prisma ORM. SQLite for local dev, PostgreSQL
  for production (one schema, switched by an env var — see below).
- **Frontend:** React + TypeScript + Vite, Tailwind CSS.
- **Auth:** JWT access/refresh tokens, roles (Admin/Manager/Cashier), manager-PIN approval
  for in-the-moment overrides (discounts, voids, refunds, creating a product from an unknown
  scan) without a role switch.
- **Testing:** Vitest (backend, 117 tests) + Playwright (frontend e2e: the main POS flow, a
  discount-approval flow, and a customer loyalty redeem/earn flow).

> This lives at `pos/` inside a repo that also holds two unrelated existing projects
> (`client/`/`server/`, an Airbnb-style booking app, and `designer/`, a 3D model tool) — it
> was added alongside them rather than replacing anything.

## Why these architecture choices

- **Money** is always an `Int` in cents. **Quantities** are always an `Int` in "milli-units"
  (value × 1000), the same trick applied to fractional/weighed items (0.001 kg precision) —
  both exist specifically to avoid floating-point arithmetic on anything that has to add up
  exactly. See `src/lib/money.ts` / `src/lib/qty.ts`.
- **"Enum" columns are `String`, not Prisma enums.** SQLite's Prisma connector has no native
  enum support at all, which would otherwise force the two schema files to diverge. Instead,
  the allowed values live as TS literal-union types in `packages/shared` and are enforced
  with Zod at every API boundary (`src/lib/enums.ts`).
- **SQLite ↔ PostgreSQL switch:** Prisma's `datasource provider` can't be an env var, so
  `schema.sqlite.prisma` and `schema.postgresql.prisma` are kept identical except that one
  line, and `scripts/select-db.mjs` copies the right one into `schema.prisma` (gitignored)
  before `generate`/`migrate`, based on `DATABASE_PROVIDER`.
- **`StockMovement` is the ledger of record.** Every stock change — sale, refund, purchase
  receipt, adjustment, transfer, damage, count reconciliation — is one row. `StockItem` is a
  cached running total, recomputed in the same transaction as the movement that caused it.
  `recordStockMovement()` (`src/modules/inventory/stock.service.ts`) is the single function
  every other module calls to touch stock, so there's one place that does the costing math.
- **Costing is configurable** (`StoreSettings.costingMethod`): weighted-average updates a
  running cost on `StockItem`; FIFO consumes `CostLayer` rows oldest-first. Both are pure,
  independently unit-tested functions (`lib/stock.ts`, `lib/fifo.ts`) that the service layer
  wraps in persistence.
- **Lot/expiration tracking rides on the same `CostLayer` table**, created and consumed on
  every stock movement regardless of costing method (previously it only existed under FIFO).
  Under weighted-average costing the cost math is unaffected — `CostLayer` there is purely a
  lot/expiration record, consumed oldest-received-first so "what's left of batch X" stays
  accurate even when it isn't driving cost.
- **A product variant is just another `Product` row.** One with `parentProductId` set,
  linked to a non-sellable "group" parent (typically `isActive: false`). Each variant has its
  own SKU, barcode, price, and stock, so it reuses every existing stock/sales/receipt code
  path untouched instead of adding a parallel variant system — the trade-off is that a
  variant's price/stock changes are managed per-variant, not in bulk across the group.
- **Loyalty points redeem as a payment method, not a special discount.** `POST
  /sales/:id/payments` with `method: "LOYALTY"` deducts `ceil(amountCents /
  loyaltyPointValueCents)` points from the attached customer and records a normal `Payment`
  row, so redemption composes with split payments for free. Completing the sale then earns
  points only on whatever wasn't paid with points (`loyaltyPointsPerDollar`, configurable),
  which keeps a customer from minting points by redeeming points.
- **Manager-PIN approval** is one mechanism reused everywhere a cashier needs a manager's
  sign-off without logging out: discounts over a configurable threshold, voids, refunds, and
  creating a new product from an unrecognized barcode scan. A Manager/Admin acting on their
  own sale self-approves; a Cashier calls `POST /api/auth/verify-pin` first to get an
  `approverId`, then passes it along.
- **No real payment processor.** `src/modules/sales/paymentProviders.ts` defines the
  `PaymentProvider` interface a real integration (Stripe Terminal, Square, Adyen, ...) would
  implement; `MockCardProvider` approves everything except a reserved test amount (ending in
  exactly `.13`), the same way real test suites use reserved card numbers for the decline path.

## Local development

Requires Node.js 22+.

```bash
cd pos
npm install

# 1. Configure the backend
cd apps/api
cp .env.example .env            # defaults work as-is for SQLite dev
npm run db:migrate              # creates prisma/dev.db and applies migrations
npm run db:seed                 # demo users, locations, categories, products, stock

# 2. Run both apps (from pos/, in separate terminals)
npm run dev:api                 # http://localhost:4000
npm run dev:web                 # http://localhost:5173 (proxies /api to :4000)
```

Open http://localhost:5173. Demo accounts (password `password123` for all):

| Email | Role | Notes |
|---|---|---|
| admin@example.com | Admin | manages users, settings |
| manager@example.com | Manager | PIN `1234` — approves discounts/voids/refunds, adjusts stock |
| cashier@example.com | Cashier | sells at the register |

Accessories — 8 products plus an "OPI Nail Polish" variant group with 3 color/size variants),

## Environment variables (`apps/api/.env`)

| Variable | Purpose |
|---|---|
| `DATABASE_PROVIDER` | `sqlite` (dev) or `postgresql` (prod) |
| `DATABASE_URL` | `file:./dev.db` for SQLite (resolved relative to `prisma/`), or a `postgresql://...` URL |
| `JWT_ACCESS_SECRET` / `JWT_REFRESH_SECRET` | Generate with `openssl rand -base64 48`; must be set to real secrets in production |
| `JWT_ACCESS_TTL` / `JWT_REFRESH_TTL` | Token lifetimes (default `15m` / `30d`) |
| `PORT`, `NODE_ENV`, `CLIENT_ORIGIN`, `LOG_LEVEL` | Standard server config |
| `BARCODE_LOOKUP_PROVIDERS` | Comma-separated, queried in order: `upcitemdb`, `openfoodfacts`, `amazon` |
| `BARCODE_LOOKUP_TIMEOUT_MS` | Per-provider timeout before falling through to the next one |
| `UPCITEMDB_API_KEY` | Optional — the trial endpoint works without one, just rate-limited (100/day) |
| `AMAZON_PAAPI_*` | Optional — see below |

### Getting barcode lookup API keys

- **Open Food Facts** — no key needed, it's open data. Used for food/grocery.
- **UPCitemdb** (https://www.upcitemdb.com/api) — works with no key on the free trial tier
  (100 lookups/day). For higher limits, sign up and set `UPCITEMDB_API_KEY`. **Off by
  default** (not in `BARCODE_LOOKUP_PROVIDERS`'s default list) since it wasn't one of the
  two providers asked for, but the adapter is fully implemented — add `upcitemdb` to the env
  var to turn it on.
- **Amazon Product Advertising API** — requires an *approved* Amazon Associates account; PA-API
  access isn't automatic on signup. Create API credentials in Associates Central, then set
  `AMAZON_PAAPI_ACCESS_KEY`, `AMAZON_PAAPI_SECRET_KEY`, and `AMAZON_PAAPI_PARTNER_TAG`. **Note:**
  PA-API's `GetItems` operation needs an ASIN, not a UPC/EAN, so this integration uses
  `SearchItems` with the barcode as a keyword instead — a best-effort text match, not a
  guaranteed exact lookup the way the other two providers are. We don't scrape Amazon's (or
  any other retailer's) website; this only calls the official, authenticated PA-API.
- Every outcome — hit or miss — is cached by barcode (`BarcodeLookupCache`) so the same code
  never triggers a second external request. Pass `?forceRefresh=true` to bypass a cached miss.

## Production deployment (Docker Compose)

```bash
cd pos
cp apps/api/.env.example .env     # then edit JWT secrets etc. — compose reads apps/api/.env
                                   # values via the environment block below, not this file
                                   # directly; set real values as shell env vars or edit
                                   # docker-compose.yml
docker compose up --build
```

This runs Postgres, the API (migrated automatically on container start), and the frontend
behind nginx, which proxies `/api/*` to the API container over the compose network — the
browser only ever talks to one origin, so there's no CORS configuration to get right in
production. Set `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`, and the barcode-lookup variables
as real environment variables before running `docker compose up` (the compose file reads
them from the shell environment with safe-but-insecure dev defaults otherwise).

> Docker Compose wasn't runnable in the environment this was built in (no daemon available),
> so the Dockerfiles are reviewed carefully but not build-verified end-to-end. If something
> doesn't build cleanly on your machine, the most likely culprit is the npm-workspaces
> symlink for `@pos/shared` — both Dockerfiles preserve the `/repo/apps/... + /repo/packages/...`
> layout specifically so that symlink resolves; flattening the copy paths will break it.

## Running tests

```bash
# Backend: 107 Vitest tests (unit + integration against a real migrated SQLite test db)
cd pos/apps/api
npm test

# Frontend: Playwright e2e (spins up its own API + web servers against a seeded test db)
cd pos/apps/web
npm run test:e2e
```

Backend test coverage includes: tax calculation (inclusive/exclusive), discount rules and
the manager-approval threshold, barcode check-digit validation (UPC-A/EAN-13/EAN-8), stock
movement math (weighted-average and FIFO, as pure functions), and the full sale-to-receipt
flow (cart → discount → split payment → complete → stock decrement → receipt number).

The Playwright suite covers the main POS flow end to end against a real Chromium instance:
login → scan a barcode (keyboard-wedge style) → search for a second item → pay cash with
change → see the receipt — plus a discount-over-threshold/manager-PIN test and a customer
loyalty redeem/earn test. Driving the real browser caught three genuine bugs during
development (all fixed): the barcode input was stealing focus back from the product search
box on every blur; completing a sale never updated the page's local state, so starting a new
sale afterward silently failed to re-hold the (already-completed) previous one; and the
points-redemption UI only supported paying the *entire* remaining balance with points, which
broke the moment a customer's balance was worth less than the sale total.

## What's complete

- Auth (JWT + refresh rotation), roles, manager-PIN approval, audit log for sensitive actions
- Product catalog: multi-barcode, check-digit validation, search/filter, CSV import/export
- Barcode lookup: 3 providers, cached, configurable, provider fallback on timeout/error
- Inventory: multi-location stock, movements, adjustments, purchase orders (partial
  receiving), stock counts with variance reports, low-stock alerts, valuation (FIFO or
  weighted average)
- Sales: cart, line discounts with approval, hold/recall, split cash/card/loyalty-points
  payments, void, partial/full refunds, per-location sequential receipt numbers
- Product variants (e.g. nail polish by color/size) and lot/expiration batch tracking with
  an "expiring soon" report
- Customer loyalty: attach a customer to a sale, redeem points (full or partial) as a
  payment method, earn points on whatever wasn't paid with points, configurable rate
- Receipts: HTML, PDF (pdfkit), and raw ESC/POS bytes for thermal printers — all three from
  the same sale data
- Reports: daily sales summary (payment/cashier breakdown), top-sellers, slow-movers,
  inventory valuation, expiring-soon batches, CSV export; dashboard with today's numbers,
  low-stock, and expiring-soon counts
- Settings: store profile, currency/locale, costing method, discount-approval threshold,
  loyalty rate/point value
- Frontend: full POS register screen (USB scanner input, camera scanning via html5-qrcode,
  distinct success/error tones, keyboard shortcuts F2/F3/F4/F8, customer lookup/attach),
  inventory management screens (incl. variant management, lot/expiration entry), a
  customers page, reports/dashboard, settings, Docker Compose for production

## What's stubbed or simplified — test these first

- **Card payments are entirely mocked.** `MockCardProvider` always approves (except the
  reserved `.13`-ending test amount). No real processor is integrated; swapping one in means
  implementing `PaymentProvider` and collecting card details client-side via that processor's
  own SDK (never let raw card numbers hit this server).
- **Amazon barcode lookup is a keyword search, not an exact lookup** (see above) — treat its
  results as lower-confidence than UPCitemdb/Open Food Facts.
- **A cashier's line-quantity change clears any discount on that line** rather than
  recalculating it, since only the computed discount amount is persisted, not the original
  percent/fixed value. Re-apply the discount after changing quantity.
- **Held/open carts aren't auto-expired or garbage-collected.** An abandoned cart just sits
  as an `OPEN`/`HELD` sale indefinitely; there's no background job to void stale ones.
- **No email verification, password reset flow, or rate limiting on login** — the auth
  module covers hashing, JWT rotation, and role checks, but not those additional hardening
  steps.
- **Reports export CSV but not PDF** (receipts do support PDF — see above); general report
  PDF export wasn't built given the time budget.
- **The Docker Compose stack is reviewed but not build-verified** (see note above) — build
  it once in a real Docker environment before relying on it.
- **Variant price/stock/barcode changes are per-variant, not bulk-editable across the
  group** — raising the price on "OPI Nail Polish" doesn't touch its color variants; each is
  edited individually in Products.
- **Loyalty points have no expiration, tiers, or minimum-redemption rules** — they accrue
  and redeem at a flat configurable rate with no other business logic layered on.
- **No receipt delivery (email/SMS) and no customer-facing order history** — a customer
  record just tracks identity and a points balance for redemption at the register.
- Test the full sale flow (scan → cart → discount → split payment → complete → receipt)
  first, since that's the path every other feature hangs off of; then the loyalty
  redeem/earn flow and variant creation, since those are the newest and most state-heavy;
  then purchase-order receiving and stock counts.
